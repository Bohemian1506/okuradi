# /区切り

区切り: $ARGUMENTS

`CLAUDE.md` の「作業の流れ」7 と、`docs/dev-log/README.md` の手順をまとめたもの。
**手順より、間違えやすい所を思い出すために使う。**

## 1. いまの状態を数え直す（**推測で書かない**）

```
git log --oneline -1
git status --short
git branch
gh pr list --state open
gh issue list --limit 50 --json number,title,labels
```

- **Issue の件数は数え直す。** 前に書いた数を写さない
- **番組側（r-hoso）が立てた Issue が増えていることがある。** ラベルが無いので見落としやすい
- **`gh issue view <番号> --json comments` も見る。** 返事はコメントとして来る
- 開いている PR が残っていないか
- **`gh` が返す時刻は UTC。手元（WSL）は日本時間で +9時間ずれる。**
  `createdAt` をそのまま議事録に書くと9時間ずれる。経過時間も、引き算する前に揃える
  （day-4 に「半日見落とした」と書いたが、実際は約3時間40分だった）

## 2. 議事録を追記する

`docs/dev-log/day-N.md`（N は**作業した日の連番**。カレンダーの日付ではない）。
同じ日に何度も区切るときは、同じファイルに節を足す。

節に書くこと（書くことがない見出しは省く）:

- **きっかけ**: 何があって始めたか
- **検討したこと**: 出た案と、選ばなかった理由
- **決めたこと**: 決定と理由。**ユーザーの判断は、その言葉に近い形で**
- **やったこと**: 変えたもの、閉じた・作った Issue
- **困ったこと / 学んだこと**

**失敗は消さない。** 同じ失敗の2回目・3回目なら、**何回目かを書く**。

一覧の表（`docs/dev-log/README.md`）のその日の行も直す。

## 3. 申し送りを上書きする

`docs/handoff.md`。**最新の1回分だけを書き、区切るたびに上書きする。**

- **main の位置に、コミットの番号や PR 番号を書かない**（書いた瞬間に古くなる）
- 開いている Issue の表（1で数えた数）
- 次にやること
- **まだ確かめていないこと**
- 気をつけること（今回の失敗を1行で）

**「〜だから使わない」と書くときは、その理由が明日も成り立つかを見る。**
成り立たないなら、**いつ見直すかを一緒に書く**（例: 「#53 を通せたら見直すもの」）。

## 4. コミットする

```
git switch main && git pull
git switch -c docs/<内容>
git add <ファイル名を1つずつ>        # git add -A を使わない
git diff --cached --name-only        # 何が入ったかを必ず見る
```

**`ep01/config.yml` には、ユーザーが GUI で保存した未コミットの変更があることがある。**
混ぜない。どうしても同じファイルを触るときは、その部分だけ外してからコミットし、あとで戻す。

## 5. PR にして、マージする

```
gh pr create --base main --title "docs: <見出し>の議事録と申し送り"
```

本文に書くこと:

- この区間でやったこと（Issue / PR の表）
- **残した失敗**
- 申し送りに足したこと
- **触っていないもの**（とくに `ep01/config.yml` を混ぜていないこと）

議事録だけの PR には、レビュー担当を呼ばなくてよい。

マージしたらブランチを消し、`main` に戻って `git status` を見る。

## 6. 最後に確かめる

- [ ] 開いている PR が無い
- [ ] ローカルのブランチが `main` だけ
- [ ] 手元の変更が、ユーザーのものだけになっている
- [ ] 議事録と申し送りで、**Issue の件数と番号が一致している**

**ここで書いた状態は、次のセッションが信じる。** 見てから書く。
