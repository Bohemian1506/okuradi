# /区切り

区切り: $ARGUMENTS

`CLAUDE.md` の「作業の流れ」7 と、`docs/dev-log/README.md` の手順をまとめたもの。
**手順より、間違えやすい所を思い出すために使う。**

## 1. いまの状態を数え直す（**推測で書かない**）

```
git log --oneline -1
git status --short
git branch
gh pr list --state open
gh issue list --limit 50 --json number,title,labels
```

- **Issue の一覧は見直す。** 前に書いたものを写さない（申し送りに件数は書かない）
- **番組側（r-hoso）が立てた Issue が増えていることがある。** ラベルが無いので見落としやすい
- **こちらから r-hoso に立てた Issue も見る。** 返事は向こうに来る（2026-09-22 に #47 を立てた）。
  `gh issue list --repo Bohemian1506/r-hoso --state all --limit 10`
- **`gh issue view <番号> --json comments` も見る。** 返事はコメントとして来る
- 開いている PR が残っていないか
- **`gh` が返す時刻は UTC。手元（WSL）は日本時間で +9時間ずれる。**
  `createdAt` をそのまま議事録に書くと9時間ずれる。経過時間も、引き算する前に揃える
  （day-4 に「半日見落とした」と書いたが、実際は約3時間40分だった）

## 2. 議事録を追記する

`docs/dev-log/day-N.md`（N は**作業した日の連番**。カレンダーの日付ではない）。
同じ日に何度も区切るときは、同じファイルに節を足す。

### まず、その日の冒頭のまとめを測り直す

```
docs/dev-log/day-stats.sh
```

マージした PR の数、**文書とそれ以外に分けた行数**、新しく足したファイルが出る。
**その数字で冒頭を書き直す。前の版から写さない。**

day-4 に、朝書いた「実装らしい実装はしていない日」をそのまま残し、
**夕方までに729行書いたのに直さなかった**。冒頭は1日に何度も古くなる。

### 節に書くこと（書くことがない見出しは省く）:

- **きっかけ**: 何があって始めたか
- **検討したこと**: 出た案と、選ばなかった理由
- **決めたこと**: 決定と理由。**ユーザーの判断は、その言葉に近い形で**
- **やったこと**: 変えたもの、閉じた・作った Issue
- **困ったこと / 学んだこと**

**失敗は消さない。** 同じ失敗の2回目・3回目なら、**何回目かを書く**。

一覧の表（`docs/dev-log/README.md`）のその日の行も直す。

## 3. 申し送りを上書きする

`docs/handoff.md`。**最新の1回分だけを書き、区切るたびに上書きする。**

**見出しは `## YYYY-MM-DD HH:MM（day-N の区切り）` の形で、いまの日付と時刻に書き直す**（`date '+%F %R'`）。
`/作業終了` が、この時刻より後に作業の PR が入ったかで「区切ったか」を見る（#202）。
**作業の PR で申し送りを直すときは、見出しを変えない。**

- **main の位置に、コミットの番号や PR 番号を書かない**（書いた瞬間に古くなる）
- **開いている Issue の表に、件数を書かない**（追いかけ続けないと嘘になる値。件数は `/始め` の hook が毎回出す。#210）
- **Issue の状態を書くときは、確認した日を添える**（「番組側の返事待ち（2026-09-26 に確認）」。状態は動く。#210）
- 次にやること
- **まだ確かめていないこと**
- 気をつけること（今回の失敗を1行で）

**「〜だから使わない」と書くときは、その理由が明日も成り立つかを見る。**
成り立たないなら、**いつ見直すかを一緒に書く**（例: 「#53 を通せたら見直すもの」）。

## 4. コミットする

```
git switch main && git pull
git switch -c docs/<内容>
git add <ファイル名を1つずつ>        # git add -A を使わない
git diff --cached --name-only        # 何が入ったかを必ず見る
```

**`ep01/config.yml` には、ユーザーが GUI で保存した未コミットの変更があることがある。**
混ぜない。どうしても同じファイルを触るときは、その部分だけ外してからコミットし、あとで戻す。

## 5. PR にして、マージする

```
gh pr create --base main --title "docs: <見出し>の議事録と申し送り"
```

本文に書くこと:

- この区間でやったこと（Issue / PR の表）
- **残した失敗**
- 申し送りに足したこと
- **触っていないもの**（とくに `ep01/config.yml` を混ぜていないこと）

議事録だけの PR には、レビュー担当を呼ばなくてよい。

マージしたらブランチを消し、`main` に戻って `git status` を見る。

## 6. r-hoso のセッションに知らせる

**番組側に関わることを r-hoso の Issue に書いたなら、r-hoso のセッションにも知らせる**（#210。r-hoso の `/区切り` の手順6と同じ形）。
Issue を見に行くまで気づかれないことがあるため。

```
ListAgents                      # r-hoso のセッションを探す
SendMessage(to: "<名前>", ...)
```

**送るのは「書いたから見て」だけ。**

- **決まったこと**と**判断が要ること**しか渡さない
- **「どうしましょうか」をセッション同士で相談しない。** 2つの Claude が合意すると、本人が知らないうちに決まる
- **決定の本文をメッセージに写さない。** 中身は Issue にある（正本が2つになる）
- 相手が起動していないときは送らなくてよい。**ラベル（`番組側の判断待ち`）が保険になる**
- **セッション名を申し送りに書かない。** 名前は変わる。送るときに `ListAgents` で探す
