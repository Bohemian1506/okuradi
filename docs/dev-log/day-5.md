## #124 feat: 作業を始めるときのコマンド /始め を足す

### きっかけ

「作業開始時に申し送り・メモリー・GitHub の Issue を確認するコマンドはあるか」と聞かれた。
手元を全部見たら、**開始側のコマンドは weight_dialy の `/mode` だけ**で、okuradi にはなかった。
okuradi にあるのは `/区切り`（終了側）だけ。**書き手はいるのに、読み手がいない状態だった。**

### 検討したこと

**まず、3つのうちコマンドが要るのは1つだけだと分かった。**

| 見るもの | コマンドが要るか |
|---|---|
| メモリー | 要らない。毎セッション自動で読まれる |
| Issue / PR / 手元の状態 | 要らない。`.claude/hooks/session-start-status.py` がもう出している |
| **申し送り** | **要る。読んで、実物と突き合わせる手順がなかった** |

**置き場所で3案を出した。**

- **A. okuradi に1つ作る** — `/区切り` と対になる。申し送りの場所が `docs/handoff.md` と決まっているので中身を具体的に書ける
- **B. 全リポジトリ共通（`~/.claude/commands/`）** — どこでも打てるが、申し送りの置き場所がバラバラ
  （okuradi は `docs/handoff.md`、フリーライフは memory の `project_session_handoff_*`、r-hoso と ANR は決まっていない）。
  「探しに行く」処理が要り、当たり外れが出る
- **C. 共通の骨を作ってリポジトリごとに上書き** — 一番きれいだが、**揃えるものがまだ okuradi にしかない**

**ユーザーの判断: 「実験を兼ねて A で」。**

### 決めたこと

**このコマンドの仕事は「申し送りと実物の突き合わせ」だけにする。**

Issue の一覧を出す処理は入れなかった。hook がもう出しているので、**同じものを2か所で数えると食い違う**。
hook が拾えないものは1つだけ（**Issue のコメント**）なので、そこだけ手順に入れた。
番組側（r-hoso）の返事はメッセージではなくコメントで来る。

**名前 `/始め` は仮置き。** あとから変えられる。

### やったこと

- `.claude/commands/始め.md` を新規（87行）
- `CLAUDE.md` の「作業の流れ」0 を `/始め` に（`/区切り` と対になるように）

### 通してみた（コミット2つ目）

**作りっぱなしにせず、その場で手でなぞった。** 結果、**申し送りと実物は全部一致していた**
（開いている Issue 15件・番号も全部・開いている PR 無し・未コミットは `ep01/config.yml` だけ・
r-hoso からの新しいコメント無し）。

一致していたのは良かったが、**通したことで手順の曖昧さが3つ出た**。

1. **コメントを見る Issue の選び方が「心当たりがあれば」だった** →

2. hook が出ていないときの打ち直しに、最近動いた Issue が無かった → 日付の出し方ごと足した

### 困ったこと / 学んだこと

- **手順に「心当たりがあれば」と書いたら、それは手順になっていない。**
  1 は、day-4 に番組側の Issue を3時間40分見落としたときと**同じ選び方**だった。
  見落とす人が「心当たり」で選ぶので、見落としは直らない。**選ぶ条件を、申し送りの文面から決まる形にした**
- **書いた値が、その場で古くなった。** 申し送りに「`/始め` はまだ1度も通していない」と書いた直後に手で通した。
  3つ目のコミットで「中身は手でなぞった / コマンドとしてはまだ呼べていない」の区別に直した。
  **day-4 の冒頭が古くなったのと同じ形**（書いた瞬間に自分で古くする）。**2回目**
- **「確かめたつもり」をもう一歩で踏むところだった。** このセッションから `/始め` を呼んだら見つからなかったが、
  **セッションを始めた場所が `~/workspace` で、起動時に okuradi にいなかった**。
  「再起動が要る」の証明にはならないので、**結論にせず未確認に入れた**

  決めつけずに `git fetch` と `gh pr list` で見たら、**もう一方は何も push していなかった**。
  ブランチも PR も増えていない

## #106 章はコーナーと1対1（番組側の決定と、同じ日の訂正）

### 届いて、訂正された

昼過ぎに「**章は8個**（アバン・OP・4コーナー・告知・ED）」と届いた。
その数時間後に「**8個は間違い。正しくはコーナーと1対1で、数はコーナーの数に従う**」と訂正が来た。

### アプリ側で見つけたズレ

**番組側の言う「コーナー」と、アプリの `segments` が指すものが違っていた。**

| | 中身 |
|---|---|
| 番組側の章（ep01・7つ） | OP / 今さら聞けない / ランテック通信 / 今月のパワープレイ / ざっくりITニュース / 告知 / ED |
| アプリの `series_rules`（4つ） | 今さら聞けない / ランテック通信 / 今月のパワープレイ / ざっくりITニュース |

**OP・告知・ED がアプリ側に存在しない。** `segments` の数をそのまま渡すと、多くても4にしかならない。

### 決めたこと（ユーザーの判断: 「A で行きましょう」）

**`series_rules` に OP・告知・ED を足し、`segments` に番組の並びとして並べる。**
章の数は `segments` を数えれば出るので、**`build.py` に数を書かない。**

落とした案:

- **B. 指示文で言葉として伝える** — 1行で済むが**数を保証できない**
- **C. 数の指定をやめ「コーナーと1対1」とだけ書く** — OP・告知・ED が章になるかが運任せ

B と C は「アプリは知らないが Claude は知っている」状態を作る。
次に構成が変わったとき、どこを直せばいいか分からなくなる。

**A の弱点は手間**（毎回 OP・告知・ED を並べる）。初期値にする手はあるが、**作ってから決める。**

**実装はまだしていない。** 触る所は #106 のコメントに書いた。
