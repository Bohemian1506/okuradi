## #16 docs: GUI の技術構成の決定を反映（#3）
- きっかけ: 申し送り（2026-09-17）の「次にやること 1」。#4 以降のデザインと実装は、#3 が決まらないと始められない
- 検討したこと
  - `build.py` を先に読んだ。工程が `step_scan` / `step_clean` / `step_transcribe` / `step_meta` / `step_video` という Python の関数に分かれていて（`build.py:171-425`）、`claude -p` も `call_claude`（`build.py:320`）から呼んでいる。**Python のサーバーならこの関数をそのまま呼べる**、Rails だと Ruby から別プロセスで呼ぶ形になり、進み具合とエラーの受け渡しを自分で作ることになる、と説明した
  - 上から順に、1つずつ選んでもらった（全体の構成 → 画面の形と長い処理 → `app.py` の扱い）
  - `claude -p` の呼び方は案が分かれないので、`call_claude` をそのまま使う前提として伝え、決定事項として Issue に書いた
- 決めたこと

  | 論点 | 決定 | 理由 |
  |---|---|---|
  | 全体の構成 | **FastAPI + 自前の画面** | `build.py` の工程の関数をそのまま呼べる。「おすすめででいきましょう」 |
  | 画面の形 | **素の HTML/CSS/JS**（波形は wavesurfer.js） | 「画面の具体的なデザインは web 版の Claude Design で作ろうかと思っています」。出てくるのは HTML と CSS なので、書き直さずそのまま置ける形にする。npm・Vite のビルドを増やさない |
  | 長い処理 | **サーバーの中の別スレッドで実行し、ログと状態を SSE で流す** | 処理中も画面を触れて、進み具合が見える。ffmpeg・Whisper・claude の失敗もそのまま画面に出せる。Celery + Redis は 1人で 1回分を作る用途には重い |
  | `claude -p` | **`build.py` の `call_claude` をそのまま使う** | サブスクの枠で動く今の形を変えない |
  | `app.py`（Streamlit） | **新しい GUI で 1回分を通せるまで残し、通せたら消す** | 新しい GUI ができるまで、番組を作る手段を切らさない |

- 決めなかったこと（実装のときに決める）: ディレクトリ構成と API の形、相談チャットで会話を続ける方法（`call_claude` の `resume` を使うか）
